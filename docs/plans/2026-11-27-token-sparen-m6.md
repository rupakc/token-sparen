# token-sparen M6 — Docs, wiki, site, release v1.0 and distribution — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship token-sparen **v1.0.0 (Claude Code)**: one version source, a tag-driven release that builds, checks and — only after owner approval — attests and publishes, one docs source rendered to the gh-pages site and the GitHub Wiki, a README whose Evidence section cites only public E4 results, a security and privacy review, a v1.0 upgrade/compatibility story, a triage of the deferred minors, a cold whole-repo review, and an owner-run distribution (Anthropic plugin directory, PyPI project, GitHub settings).

**Architecture:** `token_sparen/__init__.py` holds the only hand-edited version; `scripts/bump_version.py` writes it into `plugin.json` and the CHANGELOG, and `tests/test_release_consistency.py` fails on drift. User docs live once, in `docs/user/` (ordered by `docs/user/nav.toml`); `scripts/build_site.py` and `scripts/build_wiki.py` render them, deployed from **release tags only**, so the public docs always describe the released version. The plugin users install is the generated **`release/claude`** branch (plugin files only): the repo marketplace and the directory both track it, never `main`. A release is an owner-signed tag `vX.Y.Z` on `main` → `.github/workflows/release.yml`: CI gate → verify tag → build and check → draft GitHub Release → **owner approval (`release` environment)** → provenance → push `release/claude` → **owner approval (`pypi` environment)** → PyPI Trusted Publishing → publish the release.

**Tech Stack:** Python ≥ 3.11 stdlib only at runtime (unchanged). Dev/docs only: `Markdown` (Python-Markdown, pinned, new `docs` extra), `twine`, `pip-audit`. GitHub Actions: `actions/checkout`, `actions/setup-python`, `actions/upload-artifact`, `actions/download-artifact`, `actions/configure-pages`, `actions/upload-pages-artifact`, `actions/deploy-pages`, `actions/attest-build-provenance`, `pypa/gh-action-pypi-publish` — each pinned to a full commit SHA with the tag in a comment.

**Spec:** `docs/specs/2026-11-25-token-sparen-design.md` (§10.5 claims policy and release gate, §11, §12, §14 M6, §15). Consumes the M5 plan `docs/plans/2026-11-27-token-sparen-m5.md` (owner of the E4 evidence file, its schema, the gate result and the plugin-hash definition — rulings M6-B1..B3 in the M4 workspace ledger). Format: `docs/plans/2026-11-27-token-sparen-m4.md`.

**Out of M6 (recorded deferrals):** per-host zips, npm/OpenCode shim, other host manifests and host-matrix CI → M7 (v1.1). **No npm package for v1.0** (no consumer: Claude Code installs plugins from git and the CLI comes from PyPI; revisit with the OpenCode shim). Release notes come from the curated CHANGELOG, not generated from commits. No CycloneDX SBOM: runtime dependencies are empty (test-asserted); wheel/sdist carry build provenance and PyPI's default PEP 740 attestations. The interactive savings explorer (§11 gh-pages) → v1.1; v1.0 renders the Evidence as a static table. A plugin release zip asset is not built (marketplace and directory consume `release/claude`).

## Global Constraints

- Everything in the M0–M4 global constraints still binds (CLAUDE.md "Invariants", "Never commit private data").
- **No private data anywhere M6 writes or publishes** — docs, site, wiki, release notes, wheel/sdist metadata, workflow logs, commit messages. `scripts/check_denylist.py` scans the repo and, through its new `--path` mode, every generated tree (`_site/`, the wiki tree, release notes, the `release/claude` tree, unpacked sdist). **Publishing jobs run it with `--require-private-words`, which fails when `TOKEN_SPAREN_DENYLIST` is empty** (fail closed).
- **E4 evidence is consumed, never defined, by M6.** The evidence file (`e4.json` in ruling M6-B1; produced by the M5 plan's `bench.report` publish step), its schema, the gate result and `plugin_hash` are owned by the M5 plan and referenced by name. M6 code reads them only through M5's loader/function (`bench.report` schema loader, `bench.cli.plugin_hash` or whatever names M5 finally gives them; reconciled in Task 6 Step 0). Plugin hash per M6-B1 as amended by ruling N1: M5's `scripts/plugin_hash.py` (`PLUGIN_FILES`) over `.claude-plugin/plugin.json`, `hooks/`, `skills/`, `token_sparen/`; `.claude-plugin/marketplace.json` (distribution metadata) and all documentation files are **not** hashed. M6 only ever computes it on a built tree (`build_claude_tree`, git-tracked files), never on a working tree, so stray untracked files cannot break the gate.
- **Hash stability (follows from N1):** README, LICENSE, NOTICE, SECURITY.md, CHANGELOG and marketplace metadata are outside the hash, so the Evidence block, CHANGELOG dating and README prose may change after the freeze. M6 still keeps the Evidence table out of the shipped README (it links to the site's Evidence page) and ships no `CHANGELOG.md` in `release/claude`.
- **Runtime freeze (ruling N2/N5):** M6 owns the version bump (`bump_version.py`) and all runtime text. The **pre-freeze set** = Task 1 (version source, bump script), Task 2 (minor fixes), Task 3's runtime gap fixes, Task 4 (0.x migration, version skew, skill text incl. "Claude Code only") and the bump to `1.0.0` (Task 4 Step 6). These land before the M5 confirmation; the frozen commit is tagged **`v1.0.0-rc1`** (annotated; never matches the release regex) and is what M5 freezes and measures. After it, no task changes a hashed file except under the patch rule below; Tasks 5–12 are post-freeze and touch only unhashed files.
- **Release gate (spec §10.5, as amended by M5 Task 11):** a tag release passes only if the evidence file exists, its plugin hash equals the hash of the tree being released, and its gate result is `passed`. The only override is the one ruling M5-B1 allows ("not failed & documented, owner decides"; the decision file format is defined here by M6): gate result `underpowered` (never `failed`, never missing evidence) plus a committed, owner-authored `docs/release/gate-decision.toml` (`version`, `status = "underpowered"`, `decided` date, `note`), in which case README/site state the underpowered result with its CIs. The tag-push path has **no** skip flag. **Patch rule (ruling N4):** the E4 gate applies to minor and major releases (`X.Y.0`). A patch `X.Y.Z` (Z > 0) may ship without a new E4 run if (a) the README/site Evidence states the measured version and plugin hash ("measured on v1.0.0-rc1, plugin <hash12>"), (b) the patch's CHANGELOG section has a `### Runtime changes` list (or "none"), and (c) `git diff --name-only <measured ref>..HEAD` touches neither `token_sparen/params/` nor `token_sparen/learn/` (defaults or learning behaviour change → new confirmation required).
- **Owner actions are never automated.** Account-level resources, third-party publishing, signing and approvals are **OWNER ACTION** checkpoints: the controller prepares exact instructions, stops, and resumes only on the owner's confirmation. Provenance (public transparency-log entries) counts as publishing: it runs only after the `release` approval.
- Workflows: top-level `permissions: {}` (release) or `contents: read` (ci, docs); job-level grants only where listed in this plan; `contents: write` only in `draft-release`, `push-tree`, `finalize` and the docs `wiki` job; `id-token: write` only in `provenance`, `publish-pypi`, `deploy-pages`; no `secrets: inherit`, no `pull_request_target`; the only secret is `TOKEN_SPAREN_DENYLIST`, passed explicitly.
- Versions: PEP 440 in Python; tags match `^v\d+\.\d+\.\d+$` exactly (milestone tags such as `v0.4.0-m4` and RC tags never trigger a release or a docs deploy). `release/claude` only ever carries release versions.

## Review Focus

1. **Tag, version and branch disagree** (tag `v1.0.0` but package still `0.1.0.dev0`, stale `plugin.json`, tag not on `main`, tag signed by someone else): refused before anything is built. → Task 9 `test_release_check_refuses_tag_version_mismatch`, `test_release_check_refuses_stale_plugin_json`; Task 10 `test_verify_tag_checks_signer_and_main_ancestry`.
2. **Approval denied or a job fails midway**: before the `release` approval nothing public exists but a draft; after it, a failure before PyPI leaves PyPI untouched; resuming with "Re-run failed jobs" reuses the same artifacts and PyPI uses `skip-existing`. → Task 10 `test_publish_order_pypi_after_tree_push`, `test_pypi_skip_existing_and_hash_check`, `test_draft_release_step_is_idempotent`.
3. **Private data in generated output**, including when the deny-list secret is missing: the publishing job fails. → Task 3 `test_denylist_path_mode_scans_tree`, `test_require_private_words_fails_closed`; Task 5 `test_generated_trees_pass_denylist`.
4. **Upgrading from a 0.x install or mixing CLI and plugin versions** (dogfooding state from M0–M4, PyPI CLI older or newer than the plugin): state loads or is quarantined with one log line, an older reader never overwrites newer state, `doctor` names the skew. → Task 4 `test_milestone_state_loads_or_quarantines`, `test_older_reader_never_downgrades_state`, `test_doctor_reports_cli_plugin_skew`.

### Task 10: Release workflow

**Files:** Create `.github/workflows/release.yml`, `tests/test_release_workflow.py`.

**Workflow (decided).** `on: push: tags: ['v[0-9]+.[0-9]+.[0-9]+']` and `workflow_dispatch` (no inputs = dry run). Top-level `permissions: {}`. `SOURCE_DATE_EPOCH` = tagged commit time (reproducible archives).
1. `gate`: `uses: ./.github/workflows/ci.yml`, job `permissions: contents: read`, `secrets: TOKEN_SPAREN_DENYLIST: ${{ secrets.TOKEN_SPAREN_DENYLIST }}`.
2. `verify-tag` (push only; contents: read): tag object sha from `gh api repos/{repo}/git/ref/tags/{tag}` (`object.type == "tag"`, i.e. annotated) → `gh api repos/{repo}/git/tags/{sha}`: `verification.verified == true`, `verification.reason == "valid"`, tagger email equals repository variable `vars.RELEASE_TAGGER` (set by the owner, O5; not committed); tagged commit is an ancestor of `origin/main` (`git merge-base --is-ancestor`) and its subject is `chore(release): vX.Y.Z`.

The dry run stops here: nothing is pushed, attested or published.
4. `draft-release` (push only; contents: write): `gh release view $TAG || gh release create $TAG --draft --verify-tag --notes-file dist/NOTES.md`; `gh release upload --clobber` wheel, sdist, `SHA256SUMS`.
5. `provenance` (needs 4; **environment `release`**, required reviewer = owner; `attestations: write`, `id-token: write`): `actions/attest-build-provenance` on wheel and sdist.
6. `push-tree` (needs 5; contents: write): commit `dist/tree/` as a **fast-forward** commit on `release/claude` (parent = current branch head; created on first release), message `release: vX.Y.Z (plugin <hash12>)`; refuse if the remote head moved since the job started. No force-push. Only this job ever writes `release/claude`.
7. `publish-pypi` (needs 6; **environment `pypi`**, required reviewer = owner; `id-token: write`; GitHub-hosted ubuntu, no container): download `dist`, `pypa/gh-action-pypi-publish` with `skip-existing: true`, wheel + sdist only.
8. `finalize` (needs 7; contents: write): compare PyPI JSON API sha256 of both files with `SHA256SUMS` (fail on mismatch); `gh release edit $TAG --draft=false --latest`.

Approving `release` releases the plugin (`push-tree` updates the install branch); a denied `pypi` approval only withholds the CLI wheel: the GitHub Release stays a draft until `pypi` is approved or the owner publishes the draft by hand (release skill says so).

Resume rule (documented in the release skill): after a failure, use **"Re-run failed jobs"** only (artifacts reused, hashes stable); a full re-run of a tag is allowed only before `publish-pypi` succeeded.
